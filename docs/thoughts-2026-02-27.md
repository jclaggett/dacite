*Gorm's analysis, 2026-02-27*

## The One Remaining Open Question: Network Protocol

The spec has exactly one unchecked box: **network protocol details (HTTP? Custom?)**

Here's my thinking:

### HTTP is the right answer (with caveats)

**For the remote store**, HTTP is the obvious choice:

- `GET /node/{hash}` — fetch a node by hash
- `PUT /node/{hash}` — store a node
- `HEAD /node/{hash}` — existence check (`s-has?`)

This maps directly to `IStore`. Every operation is a single request/response. The content-addressed nature means:

- **GET is infinitely cacheable** — `Cache-Control: immutable` works literally, not just as a hint
- **CDNs work out of the box** — put a CDN in front of a dacite store and you get global distribution for free
- **PUT is idempotent** — safe to retry, no coordination needed

The spec already has `GET /node/{hash}?inline_under={bytes}` for adaptive fetch, and we could add `?leaf_chunk={bytes}` for the coalescing we spec'd tonight. This is just HTTP content negotiation with query parameters.

**What HTTP gives you for free:**
- TLS (encryption + authentication)
- Authentication headers (API keys, tokens, mTLS)
- Compression (gzip/brotli on responses)
- Range requests (for partial node fetches if ever needed)
- HTTP/2 multiplexing (parallel node fetches over one connection)
- Existing proxy/load balancer infrastructure

### Where HTTP falls short

**Push notifications.** When a remote store gets a new root, how does the client learn about it? Options:

1. **Polling** — simple, wasteful. Client periodically checks for new roots.
2. **Server-Sent Events (SSE)** — `GET /roots/stream` returns a stream of new root announcements. Lightweight, HTTP-native, works through proxies.
3. **WebSocket** — bidirectional, lower latency. More complex but enables request multiplexing too.

I'd recommend **SSE for root announcements** and plain HTTP for node fetches. SSE is simpler than WebSockets, works through more infrastructure, and the root announcement use case is inherently server→client. You don't need bidirectional communication for "hey, there's a new root."

### Bulk operations

For `s-merge` (bulk insert) and `s-snapshot` (bulk read), individual HTTP requests per node are wasteful. Options:

- **Multipart POST** — `POST /nodes` with multiple nodes in one request body
- **NDJSON streaming** — stream newline-delimited JSON objects for bulk transfer
- **Binary batch** — concatenated serialized nodes with a simple framing protocol

The guarded walk (depth-limited transitive closure) is a server-side operation: `GET /walk/{hash}?depth=5&max_bytes=1048576` returning a batch of nodes.

### My recommendation for the spec

```
Protocol: HTTP/1.1+ (HTTP/2 recommended)
Content-Type: application/octet-stream (binary) or application/json (JSON mode)
Node access: GET/PUT/HEAD /node/{hash}
Bulk: POST /nodes (batch put), GET /walk/{hash} (guarded walk)
Push: SSE at GET /events (root announcements)
Auth: Bearer token or mTLS (implementation-defined)
```

Keep it simple. Don't invent a custom protocol. HTTP is boring and that's the point.

## Roadmap Analysis: What to Build Next

### The critical path: Remote Store → Examples

The roadmap says `remote store → set utilities → examples`. I agree with the ordering but want to refine the thinking.

**Remote store is the architectural unlock.** Until you can fetch nodes from a network endpoint, Dacite is a local data structure library. A good one — but local. The remote store makes it distributed, which is the entire thesis.

The implementation is straightforward:
1. An `IStore` that wraps HTTP calls to a server
2. Compose with `LayeredStore([MemStore, RemoteStore])` for transparent caching
3. A minimal HTTP server that exposes another `IStore` (could be `FileStore`)

That's maybe 200 lines of Clojure. The serialization is done. The store protocol is done. This is plumbing.

### LRU cache store — do this alongside remote store

Once you're fetching from the network, you need bounded memory. The current `MemStore` is unbounded — fine for local use, but a remote store will accumulate fetched nodes indefinitely. An LRU store slots in as:

```
LayeredStore([LRUStore(1000), FileStore, RemoteStore])
```

Hot nodes in bounded memory, warm nodes on disk, cold nodes fetched from network. This is the store hierarchy the spec describes.

### Set utilities — low priority, do whenever

`union`, `intersect`, `diff`, `negate` are pure functions on top of HAMT. No architectural dependencies. Good "snack-sized" work for when you want a break from network plumbing.

### What the roadmap is missing

**1. Diff/patch operations.** Two roots, same structure type — what changed? This is where content addressing really shines:

```clojure
(diff old-root new-root) → seq of changes
(patch root changes) → new-root
```

Walk both trees simultaneously. When hashes match, skip the subtree (nothing changed). When they diverge, recurse. This gives you O(changes) diff, not O(size). It's the killer feature for sync, collaboration, and version control — three of the five example use cases.

**2. Merge operation.** Three-way merge: given a common ancestor and two divergent roots, produce a merged result. This is the CRDT-adjacent use case. For maps, it's relatively straightforward (key-level merge with conflict detection). For vectors, it's harder (you need to align sequences). Start with map merge.

**3. Root management.** The spec talks about root hashes but there's no concept of a "named ref" — a mutable pointer to an immutable root, like a git branch. Something like:

```clojure
(set-ref! store "main" root-hash)
(get-ref store "main") → hash
(list-refs store) → {"main" hash, "backup" hash, ...}
```

This is thin — just a separate key-value store of name→hash. But it's essential for any real use case. Without it, you have to track root hashes externally.

**4. Transaction log / history.** An append-only sequence of root hashes for a given ref. Every time a ref is updated, the old root is pushed to the history. This gives you `git log` for free — walk backward through root hashes, diff adjacent pairs.

### Revised suggested order

```
remote store + LRU cache → root refs → diff/patch → examples → set utilities
```

Remote store makes it distributed. Root refs make it usable. Diff/patch makes it powerful. Examples prove it works. Set utilities come whenever.

## On the Examples

Looking at the five proposed examples, here's how I'd prioritize:

### 1. File sync (best first example)
Represent a directory tree as nested maps of blobs. Two stores, one "server" and one "client." Sync by comparing root hashes and fetching only changed subtrees. This exercises:
- All four collection types (maps for directories, blobs for files, strings for filenames)
- Remote store (the whole point)
- Diff (only fetch what changed)
- Practical utility (people understand file sync)

### 2. Version-controlled document (second)
A map with a `:history` key pointing to a vector of previous root hashes. Each edit produces a new root; the old root goes into history. This exercises:
- Root refs (mutable pointer to latest version)
- History traversal
- Diff between versions

### 3. Config management (third)
Nested maps with diff/merge. Two config sources merge into one, conflicts detected. Practical and exercises the merge operation.

### 4. Event log (fourth)
Append-only vector. Each entry can reference its predecessor's hash for chaining. Straightforward but less interesting than the others.

### 5. CRDT-style collaboration (last)
This is the hardest and most research-adjacent. Three-way merge for concurrent edits. Save it for when everything else works.

## Performance Thoughts

From the roadmap's performance section:

**Memoize scalar constructors** — do this soon. Every time you create `(d/i64 42)`, you're computing a hash. For common values (small integers, null, true, false, single-byte chars), a lookup table avoids redundant work. The byte hash table has 256 entries; single-byte scalars should just index into it.

**Print methods** — high impact for developer experience. Right now REPL output for Dacite types is probably opaque Java object references. Custom `print-method` that shows something like `#dacite/i64 42` or `#dacite/string "hello"` makes the library dramatically more approachable.

**IReduce/IKVReduce** — important for performance when processing collections. Without these, `reduce` falls back to `seq` + `first`/`rest`, which is O(n) allocation of intermediate seqs. `IReduce` can walk the tree directly.

Suggested order: **print methods → memoize scalars → IReduce → benchmarks**

Print methods first because they improve every debugging session from now on.
