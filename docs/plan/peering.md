## 1. Direction in one paragraph

Narrow the reference implementation to one thing: a **peer**. Every Dacite client (nbb/Node and browser) is both a client and a server of immutable, hash-verified entries, and peers talk over **WebRTC data channels** using the wire-v1 pack format and the rate-based reveal protocol. A portable `.cljc` core (hashing, encoding, reveal policy) is shared by every host. The JVM server and its tests remain a **regression baseline** until the nbb peer passes them; then the pure-Clojure JVM server may be retired.

The paragraph above is the Oct 30 direction with one sentence removed. That sentence said the origin server stays the authority for root updates (CAS) and for signaling. **Revised Nov 9, 2026** (Jonathan, with Grok Bot). The origin is not a peering-layer peer directory, and it does not relay signaling for the next slices. Root updates are the roots layer. Peering follows the layers below. Manual introduce, already built in M3.2 and M5.2, is enough to open a channel to a peer the operator named.

Work through M6.4 was implicitly aimed at nbb and Clojure parity. **Revised Nov 10, 2026** (Jonathan). nbb parity is the stated goal. Demos and apps, including Value Browser rendering (M6.5) and the root URL (M6.6), are parked until that parity. M6.4 (PR #49) and the first parity slice (PR #50, mem-store merge and init keying) are done. The next parity slices are LRU store keying, then file and LMDB. Peering has two phases. Peering phase 1 is interest-based transmission over WebRTC. It is largely complete and closes with a final review, which follows this note. Peering phase 2 is ICE-based discovery for peer lists, and it comes after the roots layer. Peering phase 1 and peering phase 2 name the peering layer. The Phase 0–9 headings in section 5 stay the build schedule.

### Layers

Jonathan stated these on Nov 9. The milestones from Phase 6 sit on them. Nov 10 names peering phase 1 and peering phase 2 inside the peers layer.

1. **Stores.** Content-addressable memory with about 1k bounded-size hash-to-data entries.
2. **Values.** Immutable finger trees, HAMTs, and scalar values, stored by their hashes. Hash fusing is the matrix math under the finger tree and HAMT collections.
3. **Peers.** Remote stores, with sound network policies to transfer entries efficiently, including policies for revealing large values over time and by interest. At the peering level, everything is just peers. There is no privileged origin in the peering model. Peering phase 1 is interest-based transmission over WebRTC, to a peer already named. Peering phase 2 is ICE-based discovery for peer lists, after the roots layer (Nov 10).
4. **Roots.** Mutable references to immutable values.
5. **Later layers** build on manipulating roots. A peer list belongs here. It is a conventional value, or a document that also holds a user value, published at a root.

Roots already need a way to name and update what a peer publishes. A peer list is another such value. Publication sits with roots. Peering phase 1 is: talk to a remote store under interest and rate policy, once you already have a channel to a named peer. Peering phase 2 comes after the roots layer.

### URI model for the Value Browser

The Value Browser is parked until nbb parity (Nov 10). M6.4 is built (PR #49). M6.5 and M6.6 are parked. The URI model below is what those slices use when they resume. It works from URIs the operator types.

- A URL names a peer: how you reach a remote store. A URN names a value: `urn:dacite:<hex>`.
- The access scheme is custom, for example `dacite://dacite.io` for a peer.
- The form people paste is one URI. The peer is the scheme and host. The value is the fragment: `dacite://dacite.io#urn:dacite:<hex>`. The fragment is a pure content name. It is not sent as an HTTP path. `<hex>` is the Dacite digest. The URN names that digest. The fuse math lives in the spec, not in the URN.
- A path-form HTTP URI may exist later, as a fallback: ask this HTTP endpoint for that hash when no peer channel is up. `dacite://` plus the fragment is the canonical name for "this value, from this peer".
- A URL can also name a root. A published user value and a peer list are both mutable references. The browser opens the peer named in the URL, reads that root, and walks hashes as usual. Updating the list or the published value writes a new immutable value into the same slot.
- The browser implies a rendering stage. The first demo shows scalars and text as they are, collections (HAMT, finger tree) as a navigable tree of hashes you can click through, and a raw/hex pane. Richer media types wait until a root or a convention says how to interpret the bytes.
- Manual introduce is enough for the first demo. No origin-maintained suggest list. A peer list waits for peering phase 2, after the roots layer.

## 2. Goals and non-goals

### Goals
1. One protocol and one implementation shape: peer = store tiers + reveal engine + transport.
2. A portable `.cljc` core with identical hashes and identical reveal decisions on JVM, nbb and browser.
3. A minimal nbb peer (file or LMDB store) and a browser peer (IndexedDB store), both serving reads.
4. Peering phase 1 stays a channel to a peer the operator named, and a fetch by hash, under the interest and rate policy in peer-v1. Manual introduce is enough. (Oct 30 goal 4 was signaling through the origin, plus admin-configured peers and mDNS. That origin path is set aside; config and mDNS remain Phase 7, as ways to learn a peer URL.) Peering phase 2 is ICE-based discovery for peer lists, after the roots layer.
5. nbb parity with the Clojure suite. This is the stated goal (Nov 10). The work through M6.4 was implicitly this. The first slice is PR #50 (mem-store merge and init key the way `s-get` reads them). Next is LRU store keying, then file and LMDB. The Value Browser past M6.4, the root URL, and the other demos and apps are parked until that parity. A cleaner dacite.io portal comes after that demo (Phase 8) and is parked with it.
6. A documented, evidence-based decision on retiring the JVM server.

### Non-goals (for this plan)
- Providing a peer list in peering phase 1. A peer list is a value at a root. ICE-based discovery for peer lists is peering phase 2, after the roots layer.
- Origin-integrated signaling for the peering layer: offer/answer/ICE relay through the origin, origin suggest, locality-based peer lists, and `/signal` on the JVM origin. That path was M6.1–M6.3. It is set aside (Nov 9). The docs-only draft is [PR #47](https://github.com/jclaggett/dacite/pull/47) at `58a3b28`. This plan does not merge or close that PR.
- DHT or other wide-area hash-to-holder lookup.
- TURN relay support (direct-only until measured otherwise). STUN (a public server) is used for ICE from the first WebRTC slice.
- Writes on the peer protocol. peer-v1 stays read-only: a `get` of immutable entries. Root updates are the roots layer.
- Access control beyond "serve any hash you hold" (tracked as an open question).
- QUIC/HTTP3 reveal client. The data-channel transport replaces it as the target; the existing HTTP/3 code stays as baseline, not new work.
- Python / C / C++ ports (the spec should make them possible, but we don't build them).
- Choosing final decay parameters or reveal-policy overrides (carried as open items, not blocking).
- Richer media types in the first Value Browser. Bytes wait for a root or a convention.
- The path-form HTTP URI. It is a later fallback, not the canonical name.

### Phase 1: Peer protocol spec (Tue Nov 3 to Wed Nov 4)

**M1.1. Messages and framing.** `docs/spec/peer-v1.md` draft: roles, one data channel for control plus one per request stream, message set (`hello`, `get`/reveal, `item-stream`, `ack`/`release`, `cancel`, `error`), framing on top of wire-v1 items, max message size (chunk to a safe SCTP size).

**M1.2. Verification, rates and failure rules.** Per-entry hash verification before store, "bad entry ends the session", how peer rates share the client's `R_max` and token buckets, flow control (`bufferedAmount`), ~~idle timeouts~~ (decided: there are none; a stream decays away), explicit client ack and release (this closes the wire gap in N7/N8), read-only rule, stream ids that are not the hash (fixes the N1 design flaw).
- Acceptance: a conformance list of at least 20 numbered "MUST" statements, each mapped to a planned test. Open questions 1, 3 and 4 from the peering note get a decision or an explicit "deferred".
- **Slice 2 (Nov 4): rates, flow control, token buckets, read-only rule, protocol violations** (C01, C02, C03, C16, C17, C18, C34, C35, C36, C40, C41, C45): (C45 relaxed: a new peer starts at its fair share) built and tested in `dacite.peer.rates`, `bucket`, `responder` and `client`; the lifecycle (C05 to C12), `cancel`, `ack` and `forget` are M4.
- **Status (Nov 4): spec written, in review.** `docs/spec/peer-v1.md` sections 12 and 13: 44 numbered rules (C01 to C45, C04 withdrawn: 41 MUSTs, 3 SHOULDs; 39 Decided, 0 Proposed, 5 Existing), each with a planned test, suite and milestone. Folded in as decided by Jonathan on Nov 4: the guiding principle, one shared `R_max` (open question 2), the lifecycle by dwindling interest (no idle timeout, optional cancel, renewal as a new request, bounded lifetime), a bad hash ends the session, the sent-hash record as an optimization only, and a deterministic reveal order (breadth-first by level, fixed within a level; the stochastic shuffle is deferred until peering works in a demo). Defaults Jonathan approved later on Nov 4 (now Decided): rate control by `recv-max` in each `get` (option A, no `rate` message; the stale-`recv-max` gap is accepted for v1, revisit in M5.3; C45 first had the client keep the sum of its current (decayed) `recv-max` commitments at or below `R_max`; relaxed later on Nov 4 after the slice 2 review, since a new peer could start at 1 B/s and starve: a new `get` now carries the peer's full C01/C02 share and the overshoot gap stays, accepted), the `bufferedAmount` marks, the `floor`/`tau`/`peak` clamps and lifetime bound, the 64-stream cap, the 16 384-hash record, token buckets (20/s, burst 40), the read-only rule, and the deferral of open questions 1, 3 and 4 (spec 12.13). Approved by Jonathan later on Nov 4 (now Decided): the C01 formula, C13, session-end on protocol violation (C16), root-always-sent and ack as a hint (C20, C23), C26, and the verification MUSTs (C27 to C33). No rule is still Proposed. Deferred until a working peering demo: the stochastic shuffle and its carve-out, and a bloom-filter sent-hash record.
- **Slice 1 built (Nov 4):** verify before store (C27 to C31, C33), a verification failure ends the session (C13), other sessions untouched (C15), and the ended session's outstanding hashes re-asked of another peer (C14), in portable `dacite.peer.verify` and `dacite.peer.client`, tested on the JVM and nbb with simulated peers. Slice 2 (flow control, token buckets, the read-only rule, C45) is next.
- **Guiding principle for every M1.2 rule:** a misbehaving peer can only slow its own streams. It can never starve another peer's streams or flood the client. Simple policies are gold.

**M1.3. Async store in the peer (Nov 5, built).** `dacite.peer.client`, `responder` and `verify` chain on store promises (`dacite.store.chain`) instead of unwrapping them with `store/await`, so a store that settles late works as well as the in-memory store. No protocol change. Order is kept (one frame, `request!` or `close-session!` at a time across the client; within a frame, an item is verified, then stored, before the next) and `store/mem-store` stays synchronous: its calls return plain values, not promises. A store that fails (a put refused for quota) fails that hash locally and leaves the session open: it is not a bad entry (`client/failed`). Tests: the M1.2 client and flow checks again over a late store, three new checks, and a store of real host promises (JVM and nbb). Not done: the browser peer demo over the real IndexedDB store (`dacite.store.idb` still throws `:dacite/suspend` and relies on `drive`, it does not return a late promise yet), async pack, HTTP or reveal-service paths, M4.1.

**M1.3b. IndexedDB returns promises (Nov 5, built, stacked on M1.3).** `dacite.store.idb` returns a real promise from every `IStore` method when it is called outside `drive` (inside `drive` it still suspends and replays, for the synchronous layers above it). The M1.3 peer client runs against `idb-store` on nbb with fake-indexeddb. Not done: the rooted IndexedDB store and `dacite.store.browser` still need `drive`; the browser peer demo.

**M1.3c. IndexedDB nits (Nov 5, built).** A closed database reaches the peer as `:unavailable`, then `:store-failed` (the hash fails locally, the session lives): tested. `s-reset` outside `drive` clears the cache first and holds reads until the database is cleared, so no stale node is served after it.

**M1.1a. Tighten literalizing and serializing.** Scheduled right after M1.1 (PR #7) merges, before M1.2. Source: Grok Bot's read-only investigation of Oct 31, 2026, checked against `main` @ cda5850 and PR #7; its findings and file:line references are reproduced in the items below. Paths are under `impl/clojure/src/dacite/`. The question was whether wire-v1 can carry internal finger-tree nodes as literals under a frame-sized cap. The answer is "partially yes": leaf pages are already lists of literals, and pack already picks literal or node per store node (`store/pack.cljc:556-590`, `:592-627`). What is missing is below. No code for this phase is in PR #7 except where noted.

1. **A serializer parameter for the largest literal.** Default 16 KiB, tied to the frame payload (`peer/frame.cljc` `max-payload`, 16 378 bytes; the whole literal item must fit, so 16 378 − 37 for the payload). It is separate from the pack chunk budget (`pack/default-budget`, a soft Layer-2 target) and from the leaf page budget (`lit/page-budget`). Today `encode-item`  uses one `budget` for the first two, and nothing references the frame constants. *Partly in PR #7:* `dacite.peer.items` applies the cap by size-checking the finished literal item (`items/literal-bytes`) and passes a generous gate to `encode-item`. The parameter itself, on `encode-item` and `encode-reachable`, is this phase.
2. **Sizing stays on payload bytes for now.** `size-cue` (`store/pack.cljc:169`) and `clearly-oversized?` (`:181`) keep using the measure's `:size-bytes`, as a cheap pre-filter. The cap is checked on the encoded item after `literal-of`, through the existing `pack/wire-item-size` hook (`store/pack.cljc:91-97`). *Open design item:* add an "encoded byte size" node measure, and define how it is calculated (sum of the wire-v1 sizes of the page body, including the 9 bytes a 4-byte string costs on the wire against the 4 the cue counts; whether it is part of the measure fused into the hash, which it must not be, or a cached side value). Decide before any change to the node encoding.

   *Done in M1.1a (the bounded part):* a string or blob counts its length **+ 5** (`lit/string-wire-overhead`), so a page of tiny strings stays near its budget on the wire; `null` and `negative` count 1 (an element is never free). *Review of PR #9 (S1):* every other single element also counts its **one-byte tag** (a `char` two: tag and length), and every `run` or `repeat` its **6-byte header** (a `char` run 4 more, the text length), so the page size is never below the wire size and is exact for scalars and fixed-size runs (a test compares it with the encoder). Before, a page of alternating `u8` and `char` was 8 261 bytes, over the minimum frame; now the largest node item over the adversarial mixes (alternating one-byte kinds, in groups of 1 to 5) is about 4 200.

   *Two ideas from Jonathan for the exact measure, recorded in spec 3.2 with the same analysis; neither is built:*
   - **(a) A second measure beside `size-bytes`: encoded size, a sum monoid.** It gives an exact size cue for literal-or-node and for cutting pages. The sum is only an upper bound (a run or repeat spends its header once, so an element's cost depends on its neighbors; define it "as if each element were its own item"). If it joins the measure fused into the hash, every hash changes: a wire and hash bump, so for a later version. If it is only stored beside the measure there is no hash change, but +8 bytes per measure on every node, and it cannot be checked from a spine page's bytes (like count and size, Q1).
   - **(b) The literal encoding as an in-memory cache, bounded by the cap.** Keep a node's literal bytes with the node while within the cap, and a "too big" mark above it (inherited by the nodes above, so the mark is O(1)); "shorter wins" is then a comparison, not a build. **The literal is never stored in any entry, never on the wire, never hashed; it is a cache only.** An in-memory store and a durable one therefore differ: the durable store rebuilds or lazily computes the cache on read (a miss costs time, not correctness). No wire or hash change; content addressing means no invalidation. Costs: memory (up to 16 KiB per cached node, and a literal at each level repeats its children, so bound it by size or an LRU and keep the lower levels), and the different cost profile of the two stores. The worry of bloating spine nodes does not arise when the cache is in memory only.

   No implementation in M1.1a.
3. **Fix `lit/item-payload-bytes` and `scalar-payload-bytes`** (`value/lit.cljc:328-378`). A `run` or `repeat` of `string` or `blob` counts 0 bytes (`:364-375` falls to `scalar-payload-bytes "string" nil`, `:348`; blob `:349`), so `try-append` and `try-prepend` (`value/finger_tree.cljc:314`, `:326`) let a page grow without bound: 99 453 bytes for 100 distinct 1 KB strings, 40 049 for 5 000 four-char strings. This is the likely source of the 39 753-byte page in the PR #7 fixture `item-stream-mixed` (formerly `item-stream-three-frames`). Count real sizes, then consider switching `try-append`, `try-prepend` and `split-body-at` to the encoded size.
4. **Fix issue #8** ([#8](https://github.com/jclaggett/dacite/issues/8)): add a `"blob"` branch to `intern-lit-item!` (`value/lit.cljc:294-313`, the `string` case is at `:310`). The page-body blob is a vector of ints, so convert to host bytes first (the verified sketch used `types/coerce-and-store!`). Tests for `[blob nil]`, `[blob blob]` and `[blob 1]`, run through `literal-of`, `literal-round-trips?` and `peer/msg encode-value`. When it lands, drop the map-value-only blob rule in spec 2.1 and the known issue in section 10.
5. **Decide the leaf page size.** `lit/page-budget` is hardcoded to 1024 (`value/lit.cljc:320`; used by `ft-from-run` `value/finger_tree.cljc:976`, `try-append`, `split-body-at` at `:500` and `:536`). Raising it toward 16 KiB changes golden fixtures and size-based tests, not hashes (`add-node!` hashes type and `elements_fuse`, `value/finger_tree.cljc:58-67`). Keep the spine at 32 refs a page, separate from the leaf budget. Trade-off: fewer nodes and requests against coarser dedup and a larger granule per `get`. The PR #7 fixtures `item-stream-*` are regenerated when this changes.

   *Decided (Jonathan, Nov 2): 4 KiB.* Data in `docs/notes/page-size-measurements.md`, reasons in `docs/design/leaf-chunking.md` 2g. Roughly 3.7 times fewer pages for a long string, 9% fewer total bytes, about twice the bytes a one-element edit adds; the largest node item is under 4.3 KB, which fits the new 8192 minimum frame. 16 KiB was ruled out: its pages are over one payload. No value hash changed (seven shapes compared with `main`, pinned by a test); inner page hashes did, so fixtures were regenerated.
6. **Peer frames: literal items and a capped `encode-value`.** *Done in PR #7 (Q5):* `frame.cljc` accepts `enc = 1` items, refuses a literal over one frame payload (`literal-too-large`) from its header, and packs whole items into frames; `dacite.peer.items/encode-value` writes streams under the literal rule; spec 3.2 documents it; fixtures `item-stream-literal-at-cap` and `-over-cap` pin the boundary. *Not done:* `peer/msg.cljc` `encode-value` (the control-message encoder) is not capped by itself. A control message is bounded by the string and set limits of spec 2.1 and by `encode-frame`'s `max-frame` check, so an oversized one fails at the frame, not in `encode-value`. This phase caps it at the source. *Also left here:* letting the JVM reveal service (`service/reveal.clj`, `reveal.cljc:268` `page-bytes`) emit literals for self-contained pages; optional, a page of leaves is about the same bytes.
7. **A property test** over shapes (string, blob, vector of scalars, of strings, of blobs, nested): every durable page and every emitted literal has an encoded size within the cap, and `literal-round-trips?` holds. Keep the investigation's measurement script (it builds 100,000-byte strings, blobs and a vector of 20,000 `i64` and reports node counts and the largest page) as a regression bench in `impl/clojure/dev/`. *Shorter wins:* PR #7's `items/encode-value` compares the literal with the node entries it replaces; moving that comparison into `encode-item` (`store/pack.cljc:578-590`) so HTTP pack and peers share it is part of this phase.
8. **The S3.3 clarification.** *Done in PR #7 (spec 3.3):* leaf pages (inline leaves, no `ref`) verify on their own, because the receiver recomputes `elements_fuse` from the leaves (`body-measure`, `value/finger_tree.cljc:267`). A spine node's hash checks locally against its claimed measure, but its measure depends on its children, whose measures its bytes do not hold. The spec states this and `dacite.peer.items/verify-item!` does exactly the local checks. What to do about the unchecked part (binding a spine page's measure to its children) is an open question for M1.2; see spec section 11.
9. **Cap node items at one payload (decision Q3).** After items 3 and 5 make every page at most about 4 KiB, the sender SHOULD keep each node item within one frame payload (`items/encode-value` checks it; a test builds the shapes of item 7 and asserts every node item fits). **Decided:** it reports by default (`:oversized` in the result) and throws (`:node-too-large`) only with `:strict-node-cap? true`. Receivers keep the 1 MiB `max-item`. `frame/min-max-frame` is raised from 1024 to **8192** (the largest node item, `frame/max-node-item-bytes` 5000, plus the 37-byte item header and the 6-byte envelope fit it: `frame/min-max-frame-fits-node?`), and the `hello` limits range in spec 6.1 says 8192..16384. A new fixture, `item-stream-node-spans-frames`, keeps the oversized-node-item case covered.
10. **Make reading one element cost one element.** `tree-nth*`/`scan-children` (`value/finger_tree.cljc`) call `page-child-hashes`, which interns every character of a 1 KB leaf page (a scalar hash and a store put each) to find one, so `v/nth` and `get` on any string or vector page cost about a page of work per element (about 1 ms a character). Find the element inside the page body, as `u8-page-nth` already does for bytes, and intern only that one child. PR #7 fixes only the worst caller: `pack/host-string` now walks the leaves once with `coll/seq-vals` (the JVM suite went from about 261 s to about 50 s).
11. **Do not rebuild the same literal repeatedly.** `items/encode-value` calls `literal-bytes` for the header and for every page while it chooses literal or node, and each call rebuilds the string. Cache `literal-bytes` per hash within one `encode-value` call (a map holding one string under 40 keys pays for it 40 times), or skip the attempt when the stored size cue already says the literal cannot win.
12. **M4 follow-up: delete only the failing headers.** *Decided:* when several headers wait on one root and a check fails, each header is checked on its own; the failing ones are removed and the honest ones stay (verified). The first failure still ends the session. Done (`items/resolve-pending!`, test `only-the-failing-headers-waiting-on-a-root-are-removed`).

**Node bound instead of a gate (M1.1b, built).** The sender no longer builds a value's literal to learn it is over the cap: `dacite.store.bound` bounds the literal's wire size from the node (sum of element sizes, no run or repeat compression, in memory per call, never stored, sent or hashed); over the cap, no literal is built; at or under it, the literal fits. `pack/literal-gate` is gone. The cost is compression of compressible values over the cap (they go as node items).

**Roadmap only, not built: the exact bound.** Carry each node's first and last run in the bound's summary and merge them on combine, so a run or repeat that spans pages is bounded by its real size; or give `literal-of` a byte limit that aborts when the output passes the cap.

**Status.** All twelve items are in PR "M1.1a" (branch `m1.1a-literals`, Fixes #8). Two things came up on the way and are fixed there because the 4 KiB page made them worse: building a page one element at a time was quadratic in the page budget (every append re-expanded and re-measured the page), so `lit/append-item` rewrites only the last group and `tree-conj-right!` combines the old page measure with the new element's (a 20 000-character text went from 15 s to 1 s to encode, 30 s to 1.7 s to receive; a blob of 300 KB from 25 s to 0.14 s); and a literal of a value held under many keys was rebuilt per key (`pack/*form-cache*`). Decided after review (Jonathan): `pack/default-budget` (the HTTP chunk budget, 1024) follows the leaf page size: 4 KiB as its own constant, with a test that it is at least `lit/page-budget`. Done in the next PR (branch `m1.1a-default-budget`): it changes the layout of every pack chunk and many size tests. Cost found there: a chunked durable store of the seed catalog is 1.5 times bigger on disk (27 086 against 18 381 bytes).

**WebRTC plan, approved by Jonathan (Nov 5).** M3.1 and M3.2 are cut into three slices, and M3.2 gains a thin WebSocket signaling server (origin-integrated signaling was left for the then-future M6). Nov 9 set that path aside; see Phase 6. The decisions:

- **`ITransport` is a connection that opens named channels.** One connection (one `RTCPeerConnection`, one offer/answer) carries several named channels, all negotiated in one handshake (up front, or on demand under the same names). Each channel has `send!`, `on-message!`, `buffered-amount` and `close!` (plus `on-close!` and `max-message-size` in the code: `dacite.peer.transport`, `IChannel` and `ITransport`). Messages are opaque bytes; the transport never parses a frame.
- **Peering uses `"dacite-peer"` only.** Every peer frame (`hello`, every `get`, every item response, `ack`, `cancel`, `error`) shares this one channel, and streams are told apart by the stream id in the frame envelope. The roots layer (publish and query a public root, a trusted peer suggesting a root the server then pulls with `get`; `docs/design/roots.md`) uses `"dacite-roots"` on the same connection. Peering never sees a roots frame, and roots never sees a peer frame. A connection close closes every channel; one channel's close ends only that layer's session.
- **Flow control and the frame clamp are per channel.** The 4-frame high and 1-frame low marks of C17 (spec 12.5) read the channel's `bufferedAmount`; a paused channel holds back every stream on it together (fine for v1). The `max-frame` in a side's `hello` is clamped to the channel's negotiated `maxMessageSize` (browsers often guarantee only 16 to 64 KiB, libdatachannel negotiates one), and never below the 8192 minimum, so a frame never needs splitting at the transport. A channel too small for 8192 cannot carry a session. **WebRTC exception (node-datachannel 0.33.6):** after that clamp, the WebRTC transport cuts `max-frame` again to 4096 (`frame/webrtc-max-frame`). 16 KiB frames plus a full SCTP buffer caused silent payload corruption (hash mismatch) in our tests; 4 KiB frames with 4/1 `bufferedAmount` marks were fine. The negotiated `maxMessageSize` here is 262144, so without the extra cut the hello would stay at 16384. 4096 is below the 8192 minimum, so a node item may span frames on this transport until the clamp is raised. The in-memory transport does not apply it and keeps 16384. Raise the clamp when upstream is fixed.
- **Correction recorded (Grok Bot's review):** the 4/1 marks are per *channel*, not per stream. The rate split (C01, C02) stays per *stream*: it decides when a stream may write; the buffer only decides whether the channel can take it.
- **Close ends the session.** A transport or connection close ends the peer session exactly like a protocol violation (C16): no more frames, outstanding hashes re-asked of another peer (C14), verified items stay. A close of the `dacite-peer` channel alone ends the peer session and leaves other channels open.
- **Library: `node-datachannel` first, `werift` as fallback.** `node-datachannel` (native libdatachannel through N-API, prebuilds) is fast and datachannel-focused; use it unless its prebuilds fail on Linux or Mac here. `werift` is pure TypeScript with a browser-like `RTCPeerConnection`, no native build, and slower; it is the fallback if the prebuilds block us. Browsers use their own `RTCPeerConnection` later (M5), not these libraries.
- **ICE and signaling.** STUN now (a public STUN server); TURN later (open question 6). Signaling for the nbb slices: manual first (slice 2), then a thin WebSocket relay of offer, answer and ICE candidates between two peers that name a shared room token (slice 3, built). No peer discovery, no authentication beyond the room token.

## 10. Open questions

For the next design discussions, roughly in the order they block work.

1. **Peer lists by root or by locality. Withdrawn from peering phase 1 (Nov 9).** The origin is not a peering-layer peer directory. A peer list, if one exists, is a conventional value published at a root. ICE-based discovery for that list is peering phase 2, after the roots layer (Nov 10). M6.6, parked until nbb parity, may show one as a root and nothing more. *The Nov 4 deferral* (spec 12.13) had pointed the question at M6.1 and taken locality-only as the v1 default. The old M6.1 draft (PR #47) answered it as locality only; that draft is set aside.
2. **Peer rates: answered (Jonathan, Nov 4).** A client has one shared `R_max`, split by interest across all its open requests, whichever peer serves each. Each peer also caps what it sends; a request's rate is `min(interest share, that peer's send max)`, and share a capped peer cannot use goes to the other requests. Rejected: a separate budget per peer (simpler, but several peers together could oversubscribe the client's link, which `R_max` exists to prevent). Token buckets: spec 12.11 (Decided, 20/s burst 40). See spec 12.2.
3. **Privacy:** does asking a peer for a hash reveal what the client reads? Should a probing `get` be limited to known peers or a site? (Before M8.1 is public.) *Deferred for M1.2* (spec 12.13): a deployment policy, not a wire rule; v1 says plainly that a peer learns every hash it is asked for. Nov 9: the client dials a peer the operator named (a pasted URI). Later, config or mDNS may supply that name (Phase 7). An origin suggest list does not.
4. **Access control:** may a peer serve any hash it holds, or only to clients authorized for that root? What does the authorization model (`docs/authorization.allium`) mean for peers? *Deferred for M1.2* (spec 12.13): it depends on the authorization model and on question 7; the v1 default is the non-goal above (serve any hash you hold).
5. **Browser peers:** serve by default, or opt-in? Quota policy?

7. **Who publishes a root. Withdrawn as an origin-in-peering question (Nov 9).** Peering has no privileged origin.
